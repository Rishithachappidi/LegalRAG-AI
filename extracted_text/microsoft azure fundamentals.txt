WHAT IS CLOUD COMPUTING ?​
Cloud computing means delivering computing services (servers, storage, databases, 
networking, software) over the internet ("the cloud") — instead of owning and running 
them yourself. ​
​
Before cloud: A company had to buy servers, set them up in a server room, hire IT 
staff, maintain them — all upfront cost, even before earning ₹1. 
After cloud (Azure/AWS): Rent what you need, when you need it. No hardware. Pay 
only for usage.​
​
The 5 essential characteristics ​
​
1. On-demand self-service — You provision a server yourself in 2 minutes via a portal 
or API. No calling Microsoft, no waiting for approval, no IT ticket. You click → it's live.​
​
(On-demand self-service means you can provision computing resources yourself, 
instantly, without involving any human on the provider's side. No phone calls, no 
emails, no waiting for an IT team to approve and set up your server.) 
 You need a server? You go to a portal (or run a command), click a few options, and 
within 60–90 seconds a fully functional virtual machine is running and ready for you to 
use.​
​
"without requiring human interaction with each service provider." ​
​
EXAMPLE :​
you're building a food delivery app and you're about to run a marketing campaign that 
could bring 10x normal traffic tomorrow. 
With on-demand self-service: 
●​ Tonight you log into Azure and provision 5 extra VMs — takes 10 minutes total 
●​ Campaign runs, traffic spikes, your app handles it fine 
●​ Next day you delete those 5 VMs — you pay for exactly 18 hours of usage 
●​ Total extra cost: maybe ₹800–1,200 
Without cloud, you'd either crash under the load (no spare servers) or have spent 
months buying hardware that then sits idle.​
On-demand self-service is only possible because of three things working together: 
Virtualization — physical servers are already pre-sliced into thousands of ready VMs. 
When you request one, Azure just assigns you a slice — no physical work needed. 
Automation & orchestration — Azure runs software (like Azure Resource Manager) 
that handles all provisioning, networking, storage attachment, and OS boot 
automatically. 
APIs everywhere — every action you do in the portal is actually an API call behind the 
scenes. This is why you can also automate everything with scripts — the portal and the 
CLI use the exact same API. 
 
2. Broad network access — Access your resources from any device (laptop, phone, 
even a Raspberry Pi) over standard internet protocols. Location doesn't matter.​
​
Extra info : Broad network access is specifically about how you reach the cloud — 
through standard internet from any device. It's not about provisioning, scaling, or pricing. ​
​
IDEA) 🙂​
​
Broad network access means cloud services are available over the network and 
accessible through standard mechanisms — from any device, any location, any 
time. The "broad" means it's not locked to one type of device or one special network. 
The key word here is standard. Azure doesn't make you install a proprietary client or 
connect through a special leased line. You use standard internet protocols — 
HTTP/HTTPS, TCP/IP — the same ones your browser uses every day.​
​
COMPARISON :​
 Think of it like ATM banking. Your money lives in the bank's vault. You don't need to go 
to your specific branch, talk to your specific bank manager, or use a special device. Any 
ATM, anywhere in the world, connected to the SWIFT network, gives you access to your 
money. Standard card + standard PIN + standard network = access from anywhere. ​
Your data and compute live in Azure's data centers.​
 Any device with internet access + your credentials = you can reach your 
resources. ​
 
 
 
3. Resource pooling — Azure's physical servers are shared across thousands of 
customers simultaneously (called multi-tenancy). You don't know which physical 
machine you're on — and you don't need to. Each tenant is fully isolated.​
 
4. Rapid elasticity — Resources can expand or shrink almost instantly. During the IPL 
season, Hotstar spins up hundreds of servers in minutes. After the match, they spin 
them back down. This would be impossible with physical servers.​
 
5. Measured service — Everything is metered. Storage per GB, compute per hour, API 
calls per million. You get a bill at the end of the month — just like electricity.​

1.4 – Consumption-Based Pricing (Deep Dive)  
 
Before cloud, every company had to think like a manufacturer — buy 
equipment, own it, maintain it, depreciate it. Cloud flips this completely. You 
consume services like utilities — electricity, water, internet — and pay only 
for what you actually use. 
This is the shift from CapEx to OpEx, and it changes everything about how 
businesses plan, build, and scale. 
 
The electricity analogy — why it's the perfect mental model 
You don't build a power plant to power your home. You don't buy copper 
wire, generators, transformers, or turbines. You simply plug in and use 
electricity — and at the end of the month you get a bill based on exactly 
how many units (kWh) you consumed. 
Cloud computing works identically: 
●​ You don't buy servers, routers, cooling systems, or a server room 
●​ You plug into Azure's infrastructure via the internet 
●​ At the end of the month, Azure sends you a bill based on exactly 
what you consumed — compute hours, storage GB, API calls, data 
transferred 
The moment you stop using a resource, billing stops. Just like unplugging 
an appliance stops your electricity meter.

1.5 — Benefits of Cloud Computing  
 
 
1— HIGH AVAILABILITY :  
High availability means your application keeps running even when 
individual components fail. Azure achieves this through redundancy — 
multiple copies of everything, so no single failure brings the whole system 
down. 
Azure measures HA through SLAs (Service Level Agreements) — a 
contractual guarantee of uptime 
 
Real example: An e-commerce site with 6 VMs in an availability set. A 
power breaker trips in Rack A — VMs 1, 3, 5 go down instantly. The load 
balancer detects this in seconds and routes all traffic to VMs 2, 4, 6 in Rack 
B. Users experience a blip of latency, not an outage. SLA achieved: 
99.95%.  
Load Balancer (distributes traffic, detects failures) 
The load balancer is what makes HA actually work in practice. It sits in front 
of your VMs and continuously health-checks each one. The moment a VM 
stops responding, the load balancer stops sending it traffic — automatically, 
within seconds. 
Azure Load Balancer works at Layer 4 (TCP/UDP). Azure Application 
Gateway works at Layer 7 (HTTP/HTTPS, with SSL termination, 
path-based routing). Both support: 
●​ Health probes (ping every VM every few seconds) 
●​ Automatic removal of unhealthy VMs from the pool 
●​ Automatic addition of VMs back when they recover 
●​ Session persistence (same user always goes to same VM if needed) 
 
Paytm cannot afford downtime. Every minute of downtime during Diwali 
shopping = lakhs of failed transactions. 
Their HA setup on Azure: 
●​ API VMs deployed zone-redundant across all 3 zones in Central India 
●​ Azure Load Balancer health-probes every VM every 5 seconds 
●​ Azure SQL Database with zone-redundant replicas (automatic, no 
config needed) 
●​ If any zone loses power → remaining 2 zones absorb full traffic in 
under 15 seconds 
●​ Result: 99.99% SLA = max 4.4 minutes downtime per month 
99.9% SLA requires a single VM with Premium SSD 
99.95% SLA requires an Availability Set with 2+ VMs 
99.99% SLA requires Availability Zones 
Fault domain = protection against hardware/rack failure 
Update domain = protection against planned maintenance downtime 
Azure does NOT guarantee 100% uptime — SLA is always less than 100% 
If Azure misses the SLA, you get service credits (not cash refunds) 
HA is about staying up within a region — cross-region failover is 
"reliability/disaster recovery" 
2— Scalability  
Scalability means your system can handle more load by adding resources.  
 
Real example: Flipkart's Big Billion Days sale is planned weeks in advance. 
They scale out from 500 VMs to 5,000 VMs before the sale begins. That's 
deliberate scalability. On a normal Tuesday, those extra 4,500 VMs would 
be completely wasteful  
​
3 — Elasticity  
This benefit is the smarter ongoing solution for scalability! 
 Elasticity is scalability made automatic. The system watches your resource 
usage in real time and adds or removes resources without any human 
intervention. 
Think of it like a rubber band — it stretches exactly as much as 
needed and snaps back when demand drops. No wasted capacity, no 
under-provisioning. 
Azure achieves this through Virtual Machine Scale Sets and autoscaling 
rules. You define the rules ("when CPU > 70% for 5 minutes, add 2 VMs; 
when CPU < 30% for 10 minutes, remove 2 VMs"), and Azure does the 
rest.  
 
4 — Reliability  
Reliability means the system can recover from failures and keep 
functioning — even catastrophic ones like an entire data center going 
offline.  
Azure has 60+ regions globally. Reliability comes from distributing your 
data and workloads across multiple regions so that a failure in one place 
doesn't mean total loss. 
Key mechanisms: 
●​ Geo-replication automatically copies your data to a secondary region 
(e.g., West India → South India) — if West India burns down, your 
data exists in South India 
●​ Azure Traffic Manager detects that a region is down and reroutes all 
user requests to a healthy region within seconds 
●​ Azure Site Recovery continuously replicates entire VMs to another 
region — if your primary region fails, you can failover in minutes 
Reliability vs HA — the important distinction: 
●​ High Availability = stays up despite component failures within a 
region (a VM crashes → load balancer routes to other VMs) 
●​ Reliability = survives an entire region going down (Mumbai data 
center floods → system fails over to Pune automatically) 
 
5 – SECURITY :  
 
Azure secures the infrastructure, you secure your data and access.  
Physical security: biometric access, 24/7 guards, cameras, mantraps at 
all Azure data centers 
DDoS protection: Azure absorbs distributed denial-of-service attacks at 
the network edge before they reach your app — the largest DDoS attack 
ever recorded (2.4 Tbps) was absorbed by Azure with no customer impact 
Network security: firewalls, Network Security Groups (NSGs), private 
virtual networks isolate your resources from the internet 
Encryption: all data in transit uses TLS, all data at rest is encrypted — 
your storage, databases, VMs 
Microsoft Entra ID (formerly Azure AD): enterprise-grade identity 
management — multi-factor authentication, conditional access, zero-trust 
principles 
Microsoft Defender for Cloud: continuously scans your Azure resources 
for security misconfigurations and vulnerabilities 
 
6 — Agility  
Agility means you can provision, configure, and deploy new resources 
extremely fast — in minutes instead of the weeks it used to take with 
physical hardware.

Azure Virtual Machines & Availability Sets  
The mental model first  
A Virtual Machine is a software-defined computer running inside 
Azure's physical servers. It has its own CPU, RAM, storage, OS, network 
interface — everything a physical computer has — but it exists purely as 
software. You interact with it exactly like a real computer: SSH in, install 
software, run code, host websites.  
Azure takes one massive physical server and slices it into dozens of 
isolated VMs using a hypervisor. Each VM thinks it owns the hardware, 
but it's actually sharing it with other customers — completely isolated from 
them.  
You create a Windows VM in Azure. Then you connect to it from your 
laptop using Remote Desktop. It feels like you are using another computer, 
but that computer is actually running in Azure.  
Resource Group — the logical folder this VM lives in. Always create one 
per project.  
How to create virtual machines 
In the search bar, type Virtual machines and open it. 
Click Create > Azure virtual machine. 
In the Basics tab, fill in: 
●​ Subscription: choose your Azure subscription 
●​ Resource group: select existing or click Create new 
●​ Virtual machine name: enter a name, like myVM 
●​ Region: choose a location, like East US or Central India 
●​ Image: choose OS, like Windows Server or Ubuntu 
●​ Size: choose CPU/RAM size 
Under Administrator account: 
●​ For Windows: enter username and password 
●​ For Linux: choose SSH key or password, then enter username 
Under Inbound port rules: 
●​ For Windows VM, allow RDP 3389 
●​ For Linux VM, allow SSH 22 
Click Next: Disks. 
●​ Choose OS disk type, usually Standard SSD or Premium SSD. 
Click Next: Networking. 
●​ Azure can create a virtual network, subnet, public IP, and network 
security group automatically. 
●​ Keep defaults if you are learning. 
Click Next: Management. 
●​ Keep default settings unless you need monitoring or auto-shutdown. 
Click Review + create. 
Azure validates the settings. If validation passes, click Create. 
Wait for deployment to finish, then click Go to resource. 
 
 
WHAT WE CONTROL ON  A VM 
 
 
 
On VMs: 
●​ VMs are IaaS — you manage the OS and above 
●​ VMs can run Windows or Linux 
●​ You pick the size (CPU/RAM) and can resize later 
●​ VM pricing is per-hour; deallocate to stop compute billing 
●​ Storage disk always bills even when VM is deallocated 
●​ You can SSH (Linux) or RDP (Windows) into a VM 
On Availability Sets: 
Availability sets help protect your app from single hardware failures 
and planned maintenance downtime.  
Availability Sets require a Load Balancer 
An Availability Set alone doesn't give you HA — your app must be behind a 
Load Balancer so traffic can actually be routed away from the failed VM to 
the healthy ones. Without a load balancer, your VMs are spread across 
racks but users still hit one specific VM — if that one fails, they see an 
error. 
The load balancer health-probes every VM every few seconds. VM goes 
down → load balancer stops routing to it → users only hit healthy VMs.  
 
●​ Fault domain = protection against hardware/rack failure (unplanned) 
●​ Update domain = protection against planned maintenance reboots 
●​ Max 3 fault domains, max 20 update domains per Availability Set 
●​ SLA with Availability Set = 99.95% 
●​ Must combine with a Load Balancer for actual traffic failover 
●​ Free to create — no extra charge for the Availability Set itself 
On Availability Zones: 
Zones give higher protection than Availability Sets because they 
separate resources across different data center location  
 
●​ Physically separate buildings within one region 
●​ 3 zones per supported region 
●​ SLA = 99.99% — higher than Availability Sets 
●​ Protection against whole data center failure 
●​ Zone-redundant services: deploy once, Azure replicates across 
zones automatically 
●​ Zone-pinned services: you choose which zone to deploy in 
Key exam traps: 
●​ Stopping a VM from inside the OS ≠ stopping billing. Must "Stop 
(Deallocate)" from Azure portal 
●​ An Availability Set alone does NOT guarantee your app stays up — 
you need a Load Balancer too 
●​ Availability Zones are stronger than Availability Sets — use zones 
when available 
●​ VMs are IaaS, not PaaS — you are responsible for OS patching

WHY CONTAINERS EXIST AT ALL? 
Your app runs perfectly on your laptop (Python 3.11, specific library 
versions, your OS config) but breaks on the production server (different 
Python version, missing libraries, different OS). This mismatch between 
environments has wasted millions of developer hours historically.  
Containers solve this by packaging your app + every dependency it 
needs (libraries, runtime, config files) into one single portable unit. 
This unit runs identically everywhere — your laptop, a colleague's laptop, a 
test server, or Azure — because the entire environment travels with the 
app.  
 
Docker makes the application environment portable and repeatable, so the 
app behaves the same across different machines. 
Real life example :  
 A team has three developers — one on Mac, one on Windows, one on 
Linux. Without containers, "works on my machine" bugs eat hours every 
week. They wrap their Node.js app in a Docker container with a 
Dockerfile. Now everyone runs docker run myapp and gets the 
exact same environment — same Node version, same OS libraries — 
regardless of their actual laptop.  
Virtual Machine 
●​ Includes a full guest operating system 
●​ Has its own kernel 
●​ Needs more CPU, RAM, and disk 
●​ Starts slower 
●​ Stronger isolation 
●​ Example: running Ubuntu VM on a Windows laptop using VirtualBox 
 
Container 
●​ Shares the host machine’s OS kernel 
●​ Packages only the app, dependencies, libraries, and config 
●​ Lightweight and fast to start 
●​ Uses fewer resources 
●​ Isolation is good, but usually lighter than a VM 
●​ Example: running a Node.js app in Docker 
 
Azure Container Instances (ACI)  
ACI is the simplest possible way to run a single container in Azure — 
no VM provisioning, no cluster setup, no orchestration. You give Azure a 
container image, it runs it, you pay for exactly the seconds it ran.  
You have a Docker image (e.g., myapp:latest) 
        ↓ 
az container create --image myapp:latest --cpu 1 --memory 1.5 
        ↓ 
Azure spins up the container in ~5-10 seconds 
        ↓ 
Container runs your task 
        ↓ 
Container stops (or completes) — billing stops immediately 
 
 
 
What is orchestration? 
Running one container manually is easy. But in a real system, you may 
need 20 backend containers, 3 frontend containers, health checks, restarts, 
networking, secrets, and rolling updates. 
Simple definition: 
ACI lets you run a container directly in Azure without managing 
servers or Kubernetes.  
An orchestrator manages all that. 
A photo-sharing app needs to resize and watermark every image a user 
uploads. Instead of running a VM 24/7 waiting for uploads (paying even at 
3 AM when no one uploads anything), they trigger an ACI container 
whenever an upload happens. The container spins up, processes the 
image in 2 seconds, and shuts down. They pay for roughly 2 seconds of 
compute per upload — drastically cheaper than a constantly running VM.  
Azure Kubernetes Service (AKS)  
Common orchestration tools: 
●​ Kubernetes 
When your application grows into many containers that need to work 
together — communicating, scaling independently, recovering 
automatically from crashes — you need an orchestrator. That's Kubernetes 
(often shortened to K8s) AKS is Azure's managed Kubernetes offering.  
 
Real example: Swiggy-scale order management 3 microservices (orders, 
payments, notifications), each in separate pods Orders pod scales to 20 
replicas at lunch · payments stays at 5 · notifications at 3 
If Node 1 crashes → Kubernetes reschedules its pods onto Node 2 
automaticallyIf traffic spikes further → cluster autoscaler adds Node 3 
within minutes  
Pod — the smallest deployable unit in Kubernetes  
Node — a worker machine (a VM) that runs pods. A cluster has multiple 
nodes for redundancy and capacity. 
Cluster — the entire collection of nodes + control plane working together 
as one system. 
Control plane — Kubernetes' "brain." It decides which pods go on which 
nodes, monitors health, and handles scheduling. In AKS, Azure manages 
this for you completely free — you don't pay for the control plane, only 
for the worker node VMs. 
Deployment — a configuration that tells Kubernetes "I want 5 replicas of 
this container running, always." If one crashes, Kubernetes automatically 
starts a new one to maintain 5. 
Service — a stable networking endpoint that routes traffic to the right pods, 
even as pods get created/destroyed/rescheduled. 
Self-healing — Kubernetes' superpower 
If a pod crashes or a node fails entirely, Kubernetes automatically 
detects it and reschedules the affected pods onto healthy nodes — 
without any human intervention. This is fundamentally different from a 
traditional VM setup where a crash means manual intervention. 
ex) 
 
Swiggy's backend is split into microservices: an Orders service, a 
Payments service, and a Notifications service — each running as 
separate pods in AKS. At lunchtime, the Orders service experiences 10x 
traffic. Kubernetes' Horizontal Pod Autoscaler detects high CPU 
usage on the Orders pods and automatically scales from 4 replicas to 
20 replicas within minutes. Payments and Notifications remain 
unaffected, staying at their normal replica count. If one of the underlying 
VM nodes crashes due to a hardware fault, Kubernetes instantly 
reschedules all the pods that were on it to healthy nodes — customers 
placing orders never notice.  
 
A company doesn't want their proprietary app code published publicly on 
Docker Hub. They push all their container images to a private Azure 
Container Registry instead, and grant their AKS cluster permission to 
pull images from it. Only their own infrastructure can access these 
images — competitors or random internet users cannot.  
Simple definition: 
AKS is Azure’s managed Kubernetes service for running and 
orchestrating many containers at scale.  
Topic 2.4 — Azure Functions: Serverless Compute  
 
Think of a motion-sensor security light outside a house. It doesn't run 24/7 
burning electricity — it sits dormant, and the moment something triggers it 
(motion detected), it switches on, does its job (lights up the area), then 
switches off again. Azure Functions work identically — dormant until 
triggered, active only for the task, then back to sleep.  
We will have servers but we will never think about them at all  
A trigger is the event that causes a function to execute. This is the 
single  
 
Azure Functions offers three hosting plans, each with very different cost 
and scaling behaviors.  
Every trigger examples :  
HTTP Trigger — Real-life example: A mobile food delivery app calls GET 
/api/checkOrderStatus?id=123 — this HTTP call directly triggers a function that 
queries the database and returns the order status. No app server is running 24/7; the 
function only exists for the duration of that request. 
Timer Trigger — Real-life example: An e-commerce site needs to send "your cart is 
waiting" reminder emails every night at 2 AM. A Timer-triggered function runs on a cron 
schedule (0 0 2 * * *), checks for abandoned carts, sends emails, and goes back to 
sleep until the next night. 
Blob Storage Trigger — Real-life example: A user uploads a profile picture to Azure 
Blob Storage. This automatically triggers a function that resizes the image into 
thumbnail, medium, and full sizes, then saves them back — without the upload process 
ever needing to call an API explicitly. 
Queue Trigger — Real-life example: When a customer places an order on Swiggy, the 
order is pushed into an Azure Storage Queue. A Queue-triggered function picks it up, 
processes the payment, and updates the order status — decoupling the "place order" 
action from the "process payment" logic so the user's app stays fast and responsive. 
Cosmos DB Trigger — Real-life example: A multiplayer game stores player scores in 
Cosmos DB. Whenever a new high score is inserted, a Cosmos DB-triggered function 
fires automatically to update the global leaderboard cache, without the game client 
needing to call a separate API. 
 
Event Hub Trigger — Real-life example: A fleet of delivery bikes sends GPS location

3.2 Azure Storage Redundancy Options  
Azure Storage redundancy means Azure keeps extra copies of your 
data so that your data is not lost if hardware, server, rack, data center, or 
even a region has a problem.  
If you store a dress image in Azure Storage, Azure does not keep only one 
copy. It keeps multiple copies depending on the redundancy option you 
choose. 
Azure has these important redundancy types: 
1.​ LRS - Locally Redundant Storage 
2.​ ZRS - Zone-Redundant Storage 
3.​ GRS - Geo-Redundant Storage 
4.​ RA-GRS - Read-Access Geo-Redundant Storage 
5.​ GZRS - Geo-Zone-Redundant Storage 
6.​ RA-GZRS - Read-Access Geo-Zone-Redundant Storage 
 
1. LRS - Locally Redundant Storage 
LRS full form: Locally Redundant Storage 
LRS keeps 3 copies of your data inside a single physical location in one 
Azure region. 
It protects against: 
●​ disk failure 
●​ server failure 
●​ rack failure 
 
2. ZRS - Zone-Redundant Storage 
ZRS full form: Zone-Redundant Storage 
ZRS keeps copies of your data across multiple availability zones in the 
same Azure region. 
Availability zones are separate physical data center locations inside one 
region. 
3. GRS - Geo-Redundant Storage 
GRS full form: Geo-Redundant Storage 
GRS keeps your data in your main region and also copies it to another 
paired Azure region far away. 
3 copies in the primary region 
3 copies in the secondary region 
It protects against: 
●​ local hardware failure 
●​ data center failure 
●​ full primary region disaster 
4. RA-GRS - Read-Access Geo-Redundant Storage 
RA-GRS full form: Read-Access Geo-Redundant Storage 
RA-GRS is like GRS, but with one extra benefit: 
You can read data from the secondary region also. 
RA-GRS keeps data in another region and allows read access to that 
backup region  
This is useful when the primary region is slow or unavailable. Your app 
may still read data from the secondary region.  
5. GZRS - Geo-Zone-Redundant Storage 
GZRS full form: Geo-Zone-Redundant Storage 
GZRS combines ZRS and GRS. 
It stores data: 
●​ across multiple availability zones in the primary region 
●​ also copies data to a secondary region 
6. RA-GZRS - Read-Access Geo-Zone-Redundant 
Storage 
RA-GZRS full form: Read-Access Geo-Zone-Redundant Storage 
RA-GZRS is the strongest option in this list. 
It gives: 
●​ zone redundancy in the primary region 
●​ backup copy in secondary region 
●​ read access to secondary region 
A boutique stores records in multiple buildings in Hyderabad and also in 
Mumbai. If Hyderabad has a problem, staff can still read records from 
Mumbai.  
LRS = copies in one local place 
ZRS = copies in different zones 
GRS = copies in another geography/region 
RA = read access to backup region 
GZRS = zone + geo protection 
RA-GZRS = zone + geo protection + read access 
If you choose LRS, Azure keeps 3 copies in the same local place. Good for 
practice. 
If you choose ZRS, Azure keeps copies in different data center zones in the 
same region. Better for real apps. 
If you choose GRS, Azure also copies your data to another region. Good 
for disaster recovery. 
If you choose RA-GRS, your app can read from the backup region if the 
main region has trouble. 
If you choose GZRS, your data is protected across zones and another 
region. 
If you choose RA-GZRS, your data gets the strongest protection and can 
also be read from the backup region. 
So, storage redundancy is like deciding how many backup copies you 
want and where those backup copies should be kept.

4.6 Azure Key Vault Introduction  
Azure Key Vault is a cloud service used to securely store and manage 
sensitive information. 
Instead of writing secrets directly inside code, you store them safely in Key 
Vault.  
Why Do We Need Azure Key Vault? 
Imagine you are building a boutique web app. 
Your app may need: 
●​ database password 
●​ payment gateway API key 
●​ email service password 
 
database_password = "Boutique@123" 
If this code goes to GitHub or is shared with teammates, the password can 
be exposed. 
Store password in Azure Key Vault 
App reads it securely when needed 
An online shopping website stores its payment gateway API key in Azure 
Key Vault instead of keeping it inside the source code.  
Main Things Stored in Azure Key Vault 
Azure Key Vault mainly stores three types of sensitive items: 
1.​ Secrets 
2.​ Keys 
3.​ Certificates 
Secrets are private values your app needs but should not expose.  
A boutique app stores the Azure SQL Database connection string in 
Key Vault so developers do not hardcode it in the app.  
A key is used for encryption, decryption, signing, or verifying data.  
Keys are used to lock and unlock data securely.  
A bank uses encryption keys to protect customer transaction data. The 
keys are stored and managed in Key Vault. 
Certificates help websites and apps communicate securely.  
When you see this → https:// 
The website is using a certificate.  
 
1. Vault 
A vault is the main secure container where secrets, keys, and certificates 
are stored. 
Secret Name and Secret Value 
Each secret has a name and value. 
Name: DatabasePassword 
Value: BoutiqueDB@123 
Your app asks Key Vault for DatabasePassword, and Key Vault returns 
the secret value if the app has permission.  
Secret Versioning 
Key Vault keeps versions of secrets. 
If you update a secret, Key Vault can keep the old version and new version. 
A company rotates database passwords every month. Key Vault keeps 
versions so admins can manage changes safely. 
 Secret Rotation 
Secret rotation means changing secrets regularly. 
Banks and large companies rotate API keys and passwords regularly to 
reduce risk if an old secret is leaked.  
Soft delete protects against accidental deletion. 
Purge protection stops someone from permanently deleting secrets 
immediately  
Audit logs are activity records for Key Vault.  
How Azure Key Vault Works With an App  
1.​ Store database password in Azure Key Vault. 
2.​ Enable managed identity for App Service.(managed identity → no 
need of password) 
3.​ Give App Service permission to read the secret. 
4.​ App asks Key Vault for the password. 
5.​ Key Vault returns the secret securely. 
6.​ App connects to the database. 
The developer does not need to see or store the password in code.
